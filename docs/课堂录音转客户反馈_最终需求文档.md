# 课堂录音转客户反馈系统：最终需求文档

## 1. 项目背景

老师每天通常有多节课。每节课结束后，需要根据当堂课内容为家长输出一份客户反馈，内容包括：

- 本节课学习了什么
- 学生课堂表现如何
- 学生做得好的地方
- 当前存在的问题
- 后续需要改进的地方
- 课后练习建议
- 下节课学习重点

目前这些信息基本都可以从课堂过程本身得到，但老师课后需要额外花较长时间整理文字。系统目标是：

> 将课堂录音自动转写为文本，再基于课堂文本生成适合发给家长的客户反馈，从而减少老师课后书写总结的时间。

---

## 2. 核心结论

本项目第一版不建议默认做“网页端实时录音”，而建议采用更稳定的流程：

```text
上传已有课堂录音
→ 保存原始录音文件
→ 后台判断音频大小和格式
→ 必要时压缩与切片
→ 分段转写
→ 合并完整课堂文稿
→ 提取课堂结构化信息
→ 生成客户反馈
→ 老师审核、修改、复制发送
```

原因：

1. 网页端录音可能占用麦克风资源。
2. 如果老师上课使用课堂 App 进行语音沟通，同一设备上的网页录音可能影响课堂 App 的麦克风或音频路由。
3. 两小时长录音更适合后台异步处理，而不是前端长时间保持录音或实时连接。
4. 保存原始录音文件后，后续可以重新转写、重新生成反馈、追溯课堂内容。

---

## 3. MVP 目标

第一版 MVP 只解决一个核心问题：

> 老师上传一节课的录音文件后，系统自动生成一份可发给家长的课后反馈。

### 3.1 MVP 必须支持

- 创建或选择学生
- 删除学生数据
- 上传课堂录音文件
- 保存原始录音文件
- 自动识别音频大小、格式、时长
- 后台切片处理长录音
- 分段调用语音转文字接口
- 合并完整课堂转写稿
- 直接显示完整课堂转写文本，便于老师核验
- 基于转写稿生成结构化课堂总结
- 基于结构化总结生成家长反馈
- 可以选择反馈生成方式：本地 LLM 或 OpenAI 兼容 LLM 接口
- 使用本地 LLM 时，可以切换当前本机已安装的模型
- 老师可以编辑反馈内容
- 老师可以复制反馈内容
- 保存历史课程记录
- 同一局域网内其他设备可以直接访问网页

### 3.2 MVP 暂不支持

- 默认网页实时录音
- 家长端 App
- 自动发送微信消息
- 复杂排课系统
- 复杂权限系统
- 知识图谱
- 月度报告自动生成
- 多老师协同管理

## 4. 非目标与风险约束

### 4.1 不影响原始课堂 App

这是重要约束。

如果老师正在使用某个课堂 App 给学生上课，该 App 可能已经在使用：

- 麦克风
- 扬声器
- 蓝牙耳机
- 系统音频路由
- 通话模式音频通道

网页端如果同时请求麦克风权限，可能导致：

- 学生听不到老师声音
- 老师麦克风被浏览器占用
- 蓝牙耳机音质变差
- 系统切换音频模式
- 课堂 App 音频异常

因此，MVP 中：

```text
网页端录音不是主流程。
主流程必须是“上传已有录音文件”。
```

### 4.2 网页端录音只作为实验功能

如果后续要做网页端录音，必须满足：

1. 页面加载时不自动请求麦克风权限。
2. 默认入口是“上传录音文件”，不是“开始录音”。
3. “网页录音”必须放在实验功能区域。
4. 点击录音前必须弹窗提示：

```text
网页录音可能占用麦克风资源，影响正在进行的课堂 App 通话。
如发现课堂 App 声音异常，请立即停止录音，并改用上传录音文件方式。
```

5. 录音前提供 10 秒测试流程：
   - 浏览器是否能录到声音
   - 学生端是否还能听到老师声音
   - 课堂 App 是否正常
6. 任何异常情况下，立即停止网页录音。

## 5. 推荐产品流程

### 5.1 老师使用流程

```text
1. 老师登录系统
2. 选择学生
3. 创建一条课程记录
4. 上传课堂录音文件
5. 系统显示上传成功，进入“处理中”状态
6. 后台自动处理音频并转写
7. 转写完成后，系统生成课堂总结和家长反馈
8. 老师查看反馈
9. 老师必要时修改
10. 老师复制反馈并发送给家长
```

如果系统部署在老师自己的电脑上，页面还应显示：

```text
本机访问地址
局域网访问地址
```

这样同一 Wi-Fi 下的其他设备可以直接打开网页使用。

### 5.2 后台处理流程

```text
1. 接收音频文件
2. 保存原始音频到对象存储
3. 创建 lesson_recordings 记录
4. 使用 ffmpeg 获取音频元信息
5. 标准化音频格式
6. 按固定时长切片
7. 每个切片单独转写
8. 保存每个切片的 transcript
9. 按 chunk_index 合并完整 transcript
10. 调用大模型提取课堂结构化信息
11. 调用大模型生成家长反馈
12. 保存 feedback
13. 更新课程状态为 completed
```

## 6. 音频处理设计

### 6.1 原始文件必须保存

系统必须保存用户上传的原始音频文件。

原因：

- 转写失败时可以重新处理
- 模型升级后可以重新转写
- 老师可以回听课堂内容
- 有问题时可以追溯原始数据

建议记录字段：

```text
original_audio_url
original_audio_filename
original_audio_size
original_audio_duration
original_audio_format
```

### 6.2 是否需要切片

虽然小文件可以直接转写，但产品上建议统一切片。

推荐策略：

```text
无论原始文件大小如何，后端统一将音频按固定时长切片。
默认每 5 分钟一段。
```

原因：

1. 两小时录音可以拆成约 24 段，处理更稳定。
2. 某段失败后只需重试该段。
3. 前端可以显示处理进度。
4. 后续可以按时间定位课堂内容。
5. 避免单个请求过大或耗时过长。

### 6.3 切片规则

默认规则：

```text
chunk_duration = 5 minutes
chunk_001: 00:00:00 - 00:05:00
chunk_002: 00:05:00 - 00:10:00
chunk_003: 00:10:00 - 00:15:00
...
```

每个切片需要记录：

```text
chunk_index
start_time_sec
end_time_sec
chunk_audio_url
chunk_size
transcript_text
transcription_status
error_message
```

### 6.4 切片文件保存策略

推荐保存策略：

```text
原始音频：默认保存 30-180 天
切片音频：转写完成后可短期保存 7-30 天
转写文本：长期保存
生成反馈：长期保存
```

如果存储成本较高，可以：

```text
原始音频默认保存 30 天
老师可手动标记“长期保存”
切片音频转写成功后自动删除
transcript 和 feedback 长期保留
```

## 7. 状态机设计

### 7.1 课程状态 lesson.status

```text
created              已创建课程
audio_uploaded       音频已上传
audio_processing     音频处理中
transcribing         转写中
transcribed          转写完成
summarizing          课堂总结生成中
feedback_generated   客户反馈已生成
completed            老师已确认完成
failed               处理失败
```

### 7.2 切片状态 chunk.status

```text
pending              等待处理
processing           处理中
transcribing         转写中
completed            转写完成
failed               转写失败
```

### 7.3 失败重试

要求：

```text
如果某个切片失败，只重试该切片。
不要重新处理完整录音。
```

建议：

- 单个切片最多自动重试 3 次
- 超过 3 次后标记为 failed
- 允许后台管理端或老师手动重新处理

## 8. 数据库设计建议

### 8.1 students

```sql
CREATE TABLE students (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    grade TEXT,
    parent_contact TEXT,
    notes TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 8.2 lessons

```sql
CREATE TABLE lessons (
    id BIGSERIAL PRIMARY KEY,
    student_id BIGINT REFERENCES students(id),
    lesson_title TEXT,
    lesson_time TIMESTAMP,
    duration_sec INTEGER,
    status TEXT NOT NULL DEFAULT 'created',
    full_transcript TEXT,
    structured_summary JSONB,
    feedback_text TEXT,
    teacher_edited_feedback TEXT,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 8.3 lesson_recordings

```sql
CREATE TABLE lesson_recordings (
    id BIGSERIAL PRIMARY KEY,
    lesson_id BIGINT REFERENCES lessons(id),
    student_id BIGINT REFERENCES students(id),
    original_audio_url TEXT NOT NULL,
    original_audio_filename TEXT,
    original_audio_size BIGINT,
    original_audio_duration_sec INTEGER,
    original_audio_format TEXT,
    normalized_audio_url TEXT,
    upload_status TEXT DEFAULT 'uploaded',
    transcription_status TEXT DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 8.4 lesson_audio_chunks

```sql
CREATE TABLE lesson_audio_chunks (
    id BIGSERIAL PRIMARY KEY,
    recording_id BIGINT REFERENCES lesson_recordings(id),
    lesson_id BIGINT REFERENCES lessons(id),
    chunk_index INTEGER NOT NULL,
    start_time_sec INTEGER NOT NULL,
    end_time_sec INTEGER NOT NULL,
    chunk_audio_url TEXT,
    chunk_size BIGINT,
    transcript_text TEXT,
    transcription_status TEXT DEFAULT 'pending',
    retry_count INTEGER DEFAULT 0,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 8.5 feedback_templates

```sql
CREATE TABLE feedback_templates (
    id BIGSERIAL PRIMARY KEY,
    template_name TEXT NOT NULL,
    template_prompt TEXT NOT NULL,
    style TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

## 10. Prompt 设计

### 10.1 课堂信息提取 Prompt

```text
你是一名经验丰富的高中数学老师。请根据以下课堂转写稿，提取本节课的关键信息。

要求：
1. 只基于转写稿内容，不要编造。
2. 必须覆盖整节课，不能只总结最后一道题。
3. 如果课堂覆盖多个题号或多个知识点，需先按前半段 / 中段 / 后半段梳理，再汇总整节课的主线内容。
4. 忽略寒暄、闲聊、吃东西、录音测试、约时间等非教学内容。
5. 优先提取跨多道题反复出现的共性问题，而不是只写单题现象。
6. 在长 transcript 场景下，先做分段摘要，再做整节课汇总。
7. 系统会先从 transcript 中提取题号和知识点提示；如果这些提示确实来自课堂内容，最终总结应尽量覆盖，不要大面积遗漏前半段内容。
8. `question_breakdown` 至少覆盖 4 条、至多覆盖 8 条不同题号或不同知识模块。
9. `feedback_required_mentions` 需要显式列出前半段必提知识点、后半段必提知识点，以及反馈里必须写到的共性问题，供最终家长反馈阶段直接消费。
10. 对于长 transcript，不要求本地小模型在最后一步一次性产出超大的最终 JSON；允许系统先做分段 JSON 摘要，再由服务端确定性合并。
11. 如果转写稿中没有明确出现某些信息，请写“未明确提及”。
12. 输出 JSON，不要输出额外解释。

课堂转写稿：
{{transcript}}

请按如下 JSON 格式输出：
{
  "lesson_content": "",
  "student_performance": "",
  "strengths": [],
  "weaknesses": [],
  "typical_examples": [],
  "correction_suggestions": [],
  "homework_suggestion": [],
  "next_lesson_focus": [],
  "covered_topics": [],
  "question_breakdown": [
    {
      "problem_ref": "",
      "topic": "",
      "teacher_focus": "",
      "student_issue": ""
    }
  ],
  "feedback_required_mentions": {
    "early_topics": [],
    "late_topics": [],
    "recurring_issues": [],
    "avoid_single_focus": ""
  },
  "lesson_segments": [
    {
      "phase": "前半段",
      "problem_refs": [],
      "knowledge_points": [],
      "student_performance": "",
      "issues": []
    }
  ],
  "recurring_weaknesses": [],
  "coverage_check": {
    "covered_early": false,
    "covered_middle": false,
    "covered_late": false,
    "not_last_problem_only": false
  }
}
```

### 10.2 家长反馈生成 Prompt

```text
你是一名高中数学老师。请根据下面的课堂结构化信息，生成一段适合发给家长的课后反馈。

要求：
1. 语气专业、温和、具体。
2. 不要太官方，不要像机器生成。
3. 既要肯定学生，也要指出需要改进的地方。
4. 字数控制在 300-420 字。
5. 不要出现“根据转写稿”“AI”“模型”等字样。
6. 不要编造课堂中没有出现的内容。
7. 必须优先覆盖整节课，不能只围绕最后一道题展开。
8. 正文结构参考老师平时发给家长的课后反馈：
   - 开头问候
   - “今天这节课我主要带孩子对……进行了梳理和练习。主要包括：”
   - “掌握得较好的部分：”
   - “还需要加强的部分：”
9. 整体口吻要像老师课后手动发给家长的反馈，不要写成逐题流水账、会议纪要或“改进策略报告”。
10. 如果课堂明显是在订正一张卷子或集中梳理多道题，开头要明确写出“围绕试卷中的疑问题进行订正和梳理”这类意思，不要误写成只讲一个专题。
11. “主要包括”后面优先写 4-6 条精炼条目，至少 2 条来自前半段 / 中段内容，至少 1 条来自后半段内容。
12. “掌握得较好的部分”和“还需要加强的部分”都应写成自然段；课后建议和下节课重点自然收在最后一段，不再单独起“改进策略”标题。
13. 如果 `feedback_required_mentions.early_topics` 非空，正文里至少覆盖其中 3 个前半段知识点；如果 `late_topics` 非空，正文里至少覆盖其中 2 个后半段知识点。
14. “掌握得较好的部分”和“还需要加强的部分”各至少写 2 句，优先概括整节课反复出现的整体表现和共性问题。
15. 可以把课后建议和下节课重点合并到结尾 1-2 句，保持简洁。

课堂结构化信息：
{{structured_summary}}
```

### 10.3 输出示例

```text
今天这节课主要围绕导数综合题展开，重点练习了函数单调性、极值点判断以及含参数恒成立问题。整体来看，孩子课堂状态比较认真，能够跟着老师的思路完成主要步骤，基础求导和常规单调性判断比之前更加稳定。

比较好的地方是，孩子在发现计算问题后能够及时修正，并且愿意重新梳理解题过程，这说明学习主动性是比较好的。目前需要继续加强的是含参数问题中的分类讨论能力，尤其是定义域、临界点和导函数符号变化之间的关系，还需要形成更清晰的步骤意识。

课后建议把今天讲过的两道导数综合题重新整理一遍，重点标出每一步分类讨论的依据。下节课会继续强化导数压轴题中的参数分析和恒成立题型。
```

## 12. 后台任务设计

建议使用异步任务队列，不要让前端请求阻塞等待。

### 12.1 推荐任务

```text
process_uploaded_audio(recording_id)
    1. 获取原始音频
    2. ffmpeg 获取元信息
    3. 标准化音频
    4. 切片
    5. 创建 chunk 记录
    6. 分发转写任务

transcribe_chunk(chunk_id)
    1. 下载 chunk 音频
    2. 调用 speech-to-text API
    3. 保存 transcript_text
    4. 更新 chunk 状态

本地转写模式下，同一条录音的多个切片可以批量转写，复用同一次 Whisper 模型加载；该优化不应降低默认识别精度。

merge_transcript(lesson_id)
    1. 检查所有 chunk 是否完成
    2. 按 chunk_index 合并 transcript
    3. 保存 full_transcript

summarize_lesson(lesson_id)
    1. 根据 full_transcript 生成 structured_summary
    2. 根据 structured_summary 生成 feedback_text
    3. 更新 lesson 状态
```

### 12.2 任务依赖关系

```text
process_uploaded_audio
    ↓
transcribe_chunk x N
    ↓
merge_transcript
    ↓
summarize_lesson
    ↓
feedback_generated
```

## 13. 隐私与安全要求

课堂录音包含学生和老师的隐私信息，必须注意数据安全。

### 13.1 必须支持

- 音频文件私有存储
- 文件 URL 不应公开访问
- 后端访问需要鉴权
- 支持删除课程录音
- 支持删除学生数据
- 上传页面提示录音用途

### 13.2 建议提示文案

```text
请确认你已获得必要授权。本系统会将课堂录音用于转写和生成课后反馈。录音文件和转写文本仅用于课程总结，不会公开展示。
```

## 14. 验收标准

### 14.1 功能验收

- 可以创建学生
- 可以复制学生姓名
- 可以创建课程
- 可以上传 2 小时左右的音频文件
- 原始音频文件被保存
- 系统可以自动切片
- 每个切片可以独立转写
- 切片转写结果可以按顺序合并
- 可以生成结构化课堂总结
- 可以生成家长反馈
- 老师可以编辑并保存反馈
- 老师可以一键复制反馈
- 失败切片可以单独重试

### 14.2 稳定性验收

- 大文件上传不导致前端页面卡死
- 后台处理过程中刷新页面不丢失任务
- 某个切片失败不会导致整节课数据丢失
- 系统能显示处理进度
- 系统能显示失败原因

### 14.3 产品验收

用至少 3 节真实课堂录音测试：

1. 反馈内容是否准确
2. 是否能体现课堂重点
3. 是否能指出学生优点
4. 是否能指出学生问题
5. 语气是否适合发给家长
6. 老师修改时间是否明显减少

目标：

```text
每节课反馈整理时间从 10-20 分钟降低到 1-3 分钟审核修改。
```

## 16. 给 Codex 的实现要求摘要

请实现一个课堂录音转客户反馈的 Web MVP。

核心流程：

```text
上传课堂录音 → 保存原始文件 → ffmpeg 标准化 → 按 5 分钟切片 → 分段转写 → 合并转写稿 → 生成课堂结构化总结 → 生成家长反馈 → 老师编辑和复制
```

重要限制：

```text
1. MVP 不要默认实现网页端实时录音。
2. 不要在页面加载时请求麦克风权限。
3. 主流程必须是上传已有录音文件。
4. 必须保存原始录音文件。
5. 长音频必须支持后台异步切片处理。
6. 某个切片失败时，只重试该切片。
7. 前端必须能查询处理进度。
8. 生成反馈前，必须先得到完整 transcript 或明确标记缺失片段。
```

推荐技术栈可自行选择，例如：

```text
Frontend: React / Next.js
Backend: FastAPI / Node.js
Database: PostgreSQL / SQLite for MVP
Storage: local filesystem for MVP, later object storage
Audio Processing: ffmpeg
Async Jobs: Celery / RQ / BullMQ / background worker
LLM Provider: OpenAI API compatible interface
```

MVP 可以先使用本地文件系统保存音频，后续再替换为对象存储。

## 18. 最终判断

该方案可行。

最推荐的第一版不是实时录音，而是：

```text
上传录音文件 + 保存原始文件 + 后台切片转写 + 自动生成客户反馈
```

这种方式对老师现有课堂流程影响最小，也最不容易干扰原始课堂 App 的音频资源。
